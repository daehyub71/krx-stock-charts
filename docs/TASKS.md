### M3 사전 검토 결과 (2026-08-15 · 실측)

착수 전 anon 키로 실제 조회·쓰기를 시험했다. **데이터·권한 측면에서 착수 가능**하며, 주의점 하나가 있다.

| 검토 항목 | 결과 |
|-----------|------|
| anon 키 읽기 | 정상 — 종목 목록 200행 32KB / 일봉 3년 730행 61KB / 주봉 157행 13KB |
| 차트 조회 성능 | 일봉 1년+MA120 워밍업(366봉) **134ms, 31KB** — 클라이언트 조회로 충분 |
| RLS 쓰기 차단 | INSERT·UPDATE·DELETE **모두 차단 확인** (보안 요건 충족) |
| 데이터 완결성 | 봉이 없는 종목 **0개** (200종목 전부 적재) |

> ⚠ **Supabase REST는 응답을 기본 1000행으로 자른다.** `limit(2000)`을 요청해도 1000행만 오고,
> **오류 없이 조용히 잘린다.** 좌측 레일의 200종목 스파크라인 조회가 정확히 이 상한에 걸렸다.
> 파이프라인은 `store.fetch_daily_since`에서 `range()` 페이지네이션으로 이미 처리했고,
> 프론트도 같은 헬퍼가 필요하다 — M3 태스크에 추가했다.
>
> 이 상한은 검토 중 **오탐도 만들었다**. "봉 데이터 없는 종목 198개"로 보였는데, 확인용 조회 자체가
> 1000행에서 잘려 생긴 착시였다(실제는 0개). 조용히 잘리는 API로 완결성을 검사하면 안 된다는 사례다.

## 미해소 이슈

### ② anon 키가 프로젝트 전체를 읽는다 — **배포 블로커** (2026-08-15 발견)

**증상**: 이 웹이 실어 보낼 anon 키로 `ksc_` 테이블뿐 아니라 **같은 Supabase 프로젝트의 다른 테이블 12개**가 읽힌다.
직접 확인한 목록과 행 수:

| 테이블 | 행 | 비고 |
|--------|-----|------|
| `profiles` | 1 | `id, nickname, age_group, role` — **사용자 정보** |
| `news_articles` | 200 | |
| `libraries` | 225 | seoul-lib-events |
| `stocks_anal` | 181 | |
| `mountains` | 99 | |
| `ut_channels` / `ut_videos` | 98 / 559 | utube-trend-tracer |
| `keywords` / `trend_data` | 20 / 19 | |
| `nq_users` / `trails` / `fire_stations` | 0 | 빈 테이블이나 접근은 열려 있음 |

**왜 블로커인가**: anon 키는 브라우저 번들에 실려 공개된다. 이 키가 아직 어느 배포 사이트에도
노출된 적이 없음을 확인했으므로(utube-trend-tracer 번들 검사), **이 배포가 최초 공개가 된다.**
쓰기는 모두 막혀 있지만 읽기는 열려 있어, 배포 즉시 위 테이블이 누구에게나 열린다.

**선택지** (사용자 판단 필요)

| 안 | 방법 | 영향 |
|----|------|------|
| A | 다른 테이블에 SELECT 차단 RLS 정책 추가 (`profiles` 우선) | 근본 해결. 다른 프로젝트 동작 확인 필요 |
| B | krx-stock-charts 전용 Supabase 프로젝트를 새로 만들어 이관 | 완전 격리. 재적재 3분 + 키 교체 |
| C | 현 상태로 배포 | 위 테이블이 공개됨. `profiles`가 있어 권장하지 않음 |

> 참고: 리뷰 중 `.env`의 `KRX_PW`와 `SUPABASE_DATABASE_URL` 비밀번호가 **같은 문자열**임도 확인됐다.
> KRX 계정이 털리면 DB 직접 접속으로 이어진다 — 배포와 무관하게 분리를 권한다.


### ① 데이터 저장 위치 — ✅ 해소 (2026-08-15)

**결론**: **Supabase(PostgreSQL)** 채택, 테이블 접두어 `ksc_`. SPEC D2 재확정.

정적 JSON을 매일 GitHub에 커밋하면 파일이 통째로 새 blob이 되어 히스토리가 연 약 900MB씩 누적된다
(GitHub의 100MB는 **파일당** 한도라 개별 파일은 문제없지만, 리포 전체 권장은 1GB다).
Supabase는 이 문제가 없고, 데이터가 갱신돼도 웹 재배포가 필요 없다.

적용 완료: `supabase/schema.sql` 실행 → `ksc_tickers`·`ksc_bars`·`ksc_meta` 생성, RLS 읽기 전용 정책 적용.

### 사전 확인된 주의사항

- **파일명 한글 금지** — macOS(NFD)/Linux(NFC) 정규화 차이로 Vercel 빌드 시 ENOENT 발생.

- **MA 워밍업** — 표시 구간만 잘라 넘기면 첫 봉부터 MA선이 그려지지 않는다. 조회 시
  `표시개수 + 최장 MA주기`만큼 읽어야 한다. (시안에서 확인)
- **진행 중인 주/월 봉** — 사전 계산(D4) 채택으로, 증분 갱신 시 마지막 주봉·월봉을
  단순 유지하면 낡은 값이 고정된다. 반드시 재계산해 덮어쓴다.

### 기록

**2026-08-15 · M0 · pykrx 1.2.8은 종목목록 조회에 KRX 계정을 요구한다**
- 증상: `get_index_portfolio_deposit_file("1028")`과 `get_market_ticker_list()`가 빈 결과를 반환.
  로그에 `Expecting value: line 1 column 1 (char 0)` (= 빈 응답 본문).
- 원인: pykrx 1.2.8부터 일부 엔드포인트가 KRX 로그인 세션을 요구한다.
  임포트 시 `KRX 로그인 실패: KRX_ID 또는 KRX_PW 환경 변수가 설정되지 않았습니다` 출력.
  **OHLCV 조회(`get_market_ohlcv`)는 자격증명 없이도 정상 동작**한다 — 이것이 원인 분리의 단서였다.
- 해결: `.env`에 `KRX_ID`/`KRX_PW` 설정. `config.load_env()`가 표준 라이브러리만으로 읽어
  `os.environ`에 주입하고(기존 환경변수 우선), pykrx가 지연 로그인한다.
  `.env`는 `.gitignore`로 제외, `.env.example`만 커밋. CI에서는 리포지토리 Secrets로 주입한다.

**2026-08-15 · M0 · 종목명 일괄 조회로 약 900배 단축**
- `get_market_ticker_name(ticker)`는 종목당 1회 네트워크 호출 → 200종목에 약 285초.
- `get_market_sector_classifications(date, market)`는 **종목명과 업종을 함께** 담은
  DataFrame(942행)을 약 0.3초에 반환한다. 이쪽을 기본 경로로 쓰고, 누락 종목만 개별 보충한다.

**2026-08-15 · M0 · KRX 티커에는 문자가 섞인다 (실데이터가 잡은 버그)**
- 증상: KOSPI200 구성종목 200개 중 199개만 저장됨.
- 원인: 티커 검증 정규식을 `^\d{6}$`(숫자 6자리)로 두었는데, 실제 구성종목에
  `0126Z0`(삼성에피스홀딩스)처럼 **문자가 포함된 6자리 코드**가 존재한다.
- 해결: `^[0-9A-Z]{6}$`로 수정하고 회귀 테스트 추가(`test_accepts_alphanumeric_codes`).
- 교훈: 티커를 "숫자"로 가정하지 않는다. 이후 파일명·정렬·조회 로직 전반에 동일하게 적용한다.

**2026-08-15 · M0 · Supabase 전환 시 확인한 것**
- 기존 프로젝트에 다른 서비스 테이블(`news_articles` 등)이 있어 **모든 테이블에 `ksc_` 접두어**를 붙였다.
- 스키마 적용은 `supabase-py`로는 불가능하다(DDL 미지원). `SUPABASE_DATABASE_URL` + `psycopg`로 직접 실행했다.
  `psycopg`는 스키마 적용 전용이며 파이프라인 런타임 의존성이 아니다.
- **DB CHECK 제약을 검증의 2차 방어선으로 두었다** — 가격 > 0, `h >= max(o,c)`, `l <= min(o,c)`.
  `validate.py`가 놓쳐도 오염된 행은 저장 자체가 거부된다.
- 멱등성은 PK `(ticker, timeframe, d)` + upsert `on_conflict`로 보장된다. 실측 확인: 200행 → 재실행 → 200행.

**2026-08-15 · M1 · 실데이터가 드러낸 KRX 두 가지 특성 (9종목 실패 → 전량 복구)**

첫 백필에서 200종목 중 9종목이 검증 실패했다. 원인은 코드 버그가 아니라 **KRX 데이터의 실제 특성** 둘이었다.

1. **거래정지일** — KRX는 시·고·저가를 0으로 주고 종가에 직전 값을 유지한다(거래량 0).
   실측 예: 000880 한화 2026-07-30~08-04. 3년·200종목에서 62건.
   → 종가 기준 **보합 봉**으로 정규화한다. 날짜 구멍을 남기지 않고 마지막 알려진 가격을 보존한다.
2. **수정주가 반올림 오차** — 보정계수를 곱해 반올림하므로 원래 같았던 고가와 종가가 어긋난다.
   실측 예: 006040 동원산업 2023-09-27 — 원주가 H=C=31,000 → 보정 후 H 28,187 / C 28,188.
   **역전 폭은 전부 정확히 1원**(최대 상대오차 0.0062%)이었다.
   → 허용치를 `ROUNDING_TOLERANCE_WON = 1`로 **엄격하게** 두고 그 이내만 보정한다.
   이보다 큰 어긋남은 반올림으로 설명되지 않으므로 손대지 않고 validate가 오류로 잡게 한다.

교훈: 허용치를 감으로 정하지 않고 **실측 분포를 먼저 재서** 정했다. 넉넉하게 잡았다면 진짜 이상값까지 조용히 삼켰을 것이다.

**2026-08-15 · M2 · 종목축과 날짜축의 거래량이 미세하게 다르다**
같은 날(2026-08-14) 삼성전자 주봉 거래량이 백필 후 123,940,386 → 증분 갱신 후 123,941,596으로 1,210주 늘었다.
두 조회 경로가 집계하는 범위가 미세하게 다르다(시간외 거래 반영 시점 추정).
증분 갱신이 최신값으로 덮어쓰므로 **날짜축 값이 최종**이 된다. 정합성 문제는 아니지만,
백필 직후와 갱신 후의 거래량이 다를 수 있다는 점을 알고 있어야 한다.

**2026-08-15 · M3 · Supabase 1000행 상한이 만든 두 번째 함정**
사전 검토에서 이미 알고 있던 상한인데도, `loadSparklines`를 처음 짤 때 `.in_(tickers)` 한 번으로
200종목을 가져오려다 또 걸릴 뻔했다. 200종목 × 26주 = 5,200행이라 1000행에서 잘리고
**뒤쪽 종목의 스파크라인이 조용히 사라진다**. `fetchAllPages`로 감싸 해결했고,
"요청 200종목 → 수신 200종목, 누락 0"을 실측으로 확인하는 테스트를 남겼다.
교훈: 상한을 아는 것과 매 조회에서 기억하는 것은 다르다. 조회 헬퍼를 강제 경유시키는 편이 안전하다.
