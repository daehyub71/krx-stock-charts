# 전략 알람 기획안 — krx-stock-charts 확장

> 상태: **기획 검토안** (2026-08-16 작성). SPEC 확정 전 단계 — 가능성 판단과 선택지 제시가 목적이다.
> 전제: 기존 `ksc_bars`(2,763종목 · 2,412,261행 · 일/주/월봉)를 그대로 재사용한다.
> 목표: 매일 아침 **카카오톡 "나에게 보내기"**로 전략 신호를 받는다.

---

## 1. 결론 먼저

**다섯 전략 모두 지금 데이터로 계산 가능합니다.** 새로 수집할 것은 없습니다.
다만 확인해야 할 제약이 셋 있고, 그중 둘은 **지금 정해야 설계가 흔들리지 않습니다.**

| 판단 | 내용 |
|------|------|
| ✅ 데이터 충분 | 5개 전략 전부 현재 적재분으로 계산됨. 종목 커버리지 95~99% |
| ✅ 인프라 재사용 | 수집 파이프라인·DB·CI가 이미 있음. 배치 1개와 발송 1개만 추가 |
| ⚠️ **3년 한계** | 월봉이 37개뿐이라 "장기 횡보" 판정 구간이 좁다 (§3-A) |
| ⚠️ **거래대금 없음** | 백필분 100% NULL. 거래량(주)으로만 판단해야 함 (§3-B) |
| ⚠️ **토큰 만료** | 카카오 리프레시 토큰이 조용히 죽으면 알림이 멈춘다 (§5-C) |

## 2. 데이터 충족도 — 실측

전략이 요구하는 봉 수를 채우는 종목이 실제로 몇 개인지 DB에서 셌습니다.

| 전략이 요구하는 것 | 필요 봉 | 충족 종목 | 비율 |
|---|---|---|---|
| 월봉 20선 (MTF·턴어라운드) | 월 20 | 2,616 | 95% |
| 월봉 12개월 평균거래량 | 월 12 | 2,685 | 97% |
| 주봉 60선 | 주 60 | 2,657 | 96% |
| 주봉 볼린저 52주 | 주 52 | 2,680 | 97% |
| 주봉 20선 | 주 20 | 2,742 | 99% |
| 일봉 120선 | 일 120 | 2,729 | 99% |

**봉 개수 분포**: 월봉 최대 37 (중앙값 37) · 주봉 최대 157 · 일봉 최대 730.

미충족 종목은 대부분 **최근 상장분**(스팩·신규상장)입니다. 데이터가 쌓이면 자연히 해소되므로,
"봉이 모자라 판정 불가"를 오류가 아니라 **정상 상태(skip)**로 다루면 됩니다.

## 3. 지금 정해야 할 제약 3가지

### A. 월봉 37개 — "장기 횡보"를 어떻게 정의할 것인가 ⚠️

원안의 **장기 턴어라운드**는 "6~12개월 이상 횡보 후 직전 12개월 평균 대비 300% 거래량"을 봅니다.
월봉이 37개면 12개월 평균을 쓰는 순간 **판정 가능 구간이 25개월**로 줄고,
그 안에서 "6~12개월 횡보"를 찾으면 실질 탐색 창이 매우 좁습니다.

| 선택지 | 방법 | 트레이드오프 |
|---|---|---|
| **A-1** | 그대로 3년으로 운영 | 신호가 적게 나옴. 놓치는 종목 생김 |
| **A-2** | 백필 기간을 **5~10년**으로 확대 | 월봉 60~120개 확보. 용량 2~3배(267MB → 500MB~800MB) → **무료 한도 초과**, 유료 전환 필요 |
| **A-3** | 월봉만 장기로 별도 수집 | 일봉은 3년 유지, 월봉만 10년치. 용량 증가 미미(월봉은 전체의 4%) |

> **추천: A-3.** 월봉 10년치는 종목당 120행, 전 종목 33만 행 ≈ 35MB로 부담이 거의 없습니다.
> 일봉·주봉은 3년 그대로 두고 월봉만 늘리면 장기 전략의 판정력이 크게 좋아집니다.

### B. 거래대금이 없다 ⚠️

`ksc_bars.a`(거래대금)는 **백필분 100% NULL**입니다. 종목축 조회 경로에 없기 때문입니다.

- 원안 5개 전략은 전부 **거래량(주)** 기준이므로 **당장은 문제없습니다.**
- 다만 "거래량 300% 급증"은 저가주에서 쉽게 발생합니다. 실무에서는 거래대금으로 거르는 편이
  깨끗한데, 지금은 못 합니다.
- 필요하면 날짜축으로 3년치를 다시 훑어 채울 수 있습니다(738회 요청 ≈ 10분). **선택 사항.**

## 4. 전략별 구현 난이도

원안 그대로 옮길 수 있는지, 판단이 필요한 부분은 무엇인지만 정리합니다.
(실제 임계값 튜닝은 구현 단계에서 실데이터로 합니다.)

| 전략 | 산출 주기 | 계산 난이도 | 정의를 정해야 할 것 |
|---|---|---|---|
| **장기 턴어라운드** | 월 1회 (월말) | 중 | "횡보"의 정의 — 박스 상단/하단 폭 몇 %? 월봉 37개 제약(§3-A) |
| **주봉 추세 눌림목** | 주 1회 (금요일) | 중 | "20선 터치"의 허용 범위, "아래꼬리" 최소 길이, "거래량 급감" 기준 |
| **VCP 거래량 수축** | 매일 | **상** | 장대양봉 정의, 몸통 50% 유지 판정, 3~5일 창 슬라이딩 |
| **MTF 트리플 정배열** | 매일 | 하 | 세 조건 AND. 계산 자체는 단순하나 **신호가 적을 수 있음** |
| **밴드 스퀴즈 & 확장** | 매일 | 중 | 볼린저 기간·표준편차 배수, "52주 최저 BandWidth" 백분위 기준 |

**공통 판단 사항**

- **정렬·상한**: 전 종목 스크리닝이므로 신호가 수십~수백 개 나올 수 있습니다.
  카카오톡 한 통에 다 못 담으므로 **점수 기준 상위 N개**(예: 10개)만 보내고 나머지는 웹에서 봅니다.
- **중복 억제**: 같은 종목이 며칠 연속 같은 신호를 낼 수 있습니다. **N일 내 재알림 금지**가 필요합니다.
- **유동성 필터**: 거래량 극소 종목·스팩·우선주를 뺄지 정해야 합니다
  (현재 스팩 71종목, 우선주 165종목이 데이터에 포함돼 있습니다).

## 5. 알림 채널 — 카카오 두 갈래

### A. PlayMCP (`playmcp.kakao.com/mcp/1`) — 검토 결과

**무엇인가**: 카카오가 2025-08 베타 오픈한 **MCP 서버 플랫폼**입니다.
카카오톡 "나와의 채팅방", 톡캘린더, 카카오맵, 선물하기, 멜론 등 카카오 서비스와
외부 MCP 서버 약 200개가 등록돼 있고, Claude·ChatGPT 등에서 붙여 쓸 수 있습니다.

**우리 용도에 쓸 수 있는가**: **이 기획(매일 아침 자동 발송)에는 부적합합니다.**

| 항목 | 확인 내용 |
|------|-----------|
| 기능 | "카카오톡 나와의 채팅방" 도구가 실제로 존재 — 목적에는 맞음 |
| 인증 | 카카오 계정 **로그인 세션** 기반. 엔드포인트에 인증 없이 POST하면 **403** (직접 확인) |
| 실행 모델 | **대화형 AI 에이전트**가 사람 대신 호출하는 구조 |
| 무인 배치 | GitHub Actions처럼 사람 없는 환경에서 세션을 유지할 표준 경로가 없음 |

> **결론**: PlayMCP는 "클로드에게 말해서 카톡 보내기"에 좋은 도구입니다.
> 하지만 우리가 만들려는 건 **매일 아침 8시에 사람 없이 도는 배치**라 성격이 다릅니다.
> 다만 **탐색용으로는 값어치가 있습니다** — 저녁에 직접 붙여서
> "오늘 신호 뭐 있어?"라고 물어보는 대화형 용도로는 딱 맞습니다. (§7 참조)

### B. 카카오 REST API "나에게 보내기" — 추천

```
POST https://kapi.kakao.com/v2/api/talk/memo/default/send
```

카카오 로그인으로 받은 액세스 토큰으로 호출하면 **나와의 채팅방**에 메시지가 도착합니다.
친구에게 보내는 것과 달리 **검수 없이** 쓸 수 있고 무료입니다.

### C. 토큰 만료 — 이 기획의 진짜 운영 리스크 ⚠️

**"잘 돌던 알림이 두 달째 어느 날 조용히 멈춘다"**가 이 방식의 알려진 함정입니다.

| 토큰 | 성격 | 실패 시 |
|------|------|---------|
| 액세스 토큰 | 수 시간 단위로 만료 | 리프레시 토큰으로 자동 재발급 (정상 경로) |
| 리프레시 토큰 | 약 2개월. 사용하면 갱신되지만 **끊기면 끝** | `KOE322 expired_or_invalid_refresh_token` → **인가 코드부터 수동 재발급** |

**대응 설계 (SPEC에 넣을 것)**

1. 매일 도는 배치가 리프레시 토큰을 쓰므로 **정상 운영 중에는 만료되지 않습니다.**
2. 갱신 시 새 리프레시 토큰이 오면 **GitHub Secret을 자동 갱신**해야 합니다
   (안 하면 옛 토큰으로 계속 시도하다 만료).
3. `KOE322`가 뜨면 **조용히 실패하지 않고** Actions를 실패시켜 알림이 오게 합니다.
4. **"신호 0건이라 안 온 것"과 "고장 나서 안 온 것"을 구분**해야 합니다 →
   신호가 없어도 "오늘 신호 없음" 한 줄을 보냅니다. 침묵을 정상 상태로 두지 않습니다.

> 4번이 특히 중요합니다. 알림 시스템은 **안 오는 게 정상인 날**이 많아서,
> 고장을 알아채기까지 몇 주가 걸릴 수 있습니다.

## 6. 아키텍처 초안 — 기존 구조에 무엇을 더하나

```
[기존] 평일 18:00 KST · GitHub Actions
   pykrx → collect → resample → validate → store → ksc_bars

[추가] 평일 08:00 KST · GitHub Actions          ← 새 워크플로 1개
   ksc_bars 조회 → 전략 스크리닝 → 신호 저장 → 카카오 발송
                        │                │
                        │                └→ ksc_signals (새 테이블)
                        └→ 5개 전략 모듈 (순수 함수, TDD)

[기존] 웹                                        ← 화면 1개 추가
   krx-stock-charts.vercel.app/signals (신호 이력·상세)
```

**새로 만드는 것**

| 구성 | 내용 |
|------|------|
| `ksc_signals` 테이블 | 종목·전략·발생일·점수·근거값. 중복 억제와 이력 조회에 쓴다 |
| `strategy/` 모듈 | 전략 5개. 전부 **순수 함수**로 — 봉 배열을 받아 신호를 돌려준다 (TDD 대상) |
| `notify/kakao.py` | 나에게 보내기 발송 + 토큰 갱신 + 실패 시 명확한 오류 |
| `.github/workflows/alert.yml` | 평일 08:00 KST cron |
| 웹 `/signals` | 알림에 다 못 담은 신호를 여기서 본다 |

**기존 구조를 그대로 쓰는 것**: 수집 파이프라인, `ksc_bars`, Supabase, 검증 게이트, 배포.

## 7. 두 갈래로 나눠 가는 것을 제안합니다

| 갈래 | 채널 | 성격 | 용도 |
|------|------|------|------|
| **자동 알림** | 카카오 REST API | 무인 배치 (매일 08:00) | "오늘 이거 봐라" — 놓치지 않는 것이 목적 |
| **대화형 조회** | PlayMCP + Claude | 사람이 물을 때 | "왜 이 종목이 잡혔어?" — 파고드는 것이 목적 |

PlayMCP는 저녁에 직접 붙여 보시고, 쓸 만하면 두 번째 갈래로 붙이면 됩니다.

## 8. 확정이 필요한 결정 사항

SPEC으로 넘어가기 전에 정할 것들입니다. 추천안을 함께 적었습니다.

| ID | 항목 | 선택지 | 추천 |
|----|------|--------|------|
| A1 | 월봉 기간 | ① 3년 유지 ② 전체 5~10년 확대 ③ **월봉만 10년** | ③ — 용량 부담 거의 없이 장기 전략 판정력 확보 |
| A2 | 거래대금 | ① 안 씀 ② 3년치 소급 수집(약 10분) | ① 먼저, 필요해지면 ② |
| A3 | 전략 범위 | ① 5개 전부 ② 쉬운 것부터 2~3개 | ② — MTF·주봉 눌림목부터. VCP는 정의가 까다로워 나중에 |
| A4 | 알림 채널 | ① 카카오 REST ② PlayMCP ③ 둘 다 | ③ — 자동은 REST, 대화형은 PlayMCP (§7) |
| A5 | 발송 시각 | ① 08:00 ② 07:30 ③ 장 시작 직전 08:50 | ① |
| A6 | 신호 상한 | ① 상위 10개 ② 20개 ③ 전부 | ① + 나머지는 웹 링크 |
| A7 | 유동성 필터 | ① 전 종목 ② 스팩·우선주 제외 ③ 거래량 하위 제외 | ②+③ — 신호 품질이 크게 달라짐 |
| A8 | 신호 없는 날 | ① "없음" 발송 ② 미발송 | ① — 고장과 구분하기 위해 (§5-C) |
